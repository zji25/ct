**Домашнее задание 10. Транзакции**

1. Уровни изоляции

    1.1.1. RegisterUser
    ```sql
    -- целостность обеспечивает уникальный ключ UserId: при гонке один из инсёртов
    -- отвергнется по уникальному ограничению. 
    -- read uncommited недостаточен, тк возможен ложный отказ из‑за чтения незавершённой
    -- вставки другого пользователя или чтения удаленного пользователя
    start transaction read write isolation level read commited;
    ```
    1.1.2. ManageFlight
    ```sql
    -- обновление флагов рейса, при гонке приемлемо сохранение результата последней
    -- транзакции.
    -- read uncommited недостаточен, тк проверка прав может разрешить обновление на
    -- основе незавершенных изменений (смены пароля/прав администрирования)
    start transaction read write isolation level read commited;
    ```
    1.2.1. FreeSeats
    ```sql
    -- список свободных мест формируется одним запросом; нужен согласованный снимок без
    -- грязных чтений.
    -- read uncommited недостаточен, тк в результирующий список могут попасть места,
    -- освобождённые или занятые в незавершенных транзакциях
    start transaction read only isolation level read commited;
    ```
    1.2.2. Reserve
    ```sql
    -- аномалия косой записи не страшна, тк работаем с единственной записью.
    -- после проверок выполняется insert, целостность обеспечивает ключ (FlightId,
    -- SeatNo); при гонке один insert победит, второй корректно получит конфликт и
    -- продлит бронирование в случае с одновременной попыткой бронирования/бросит
    -- исключение при попытке покупки
    start transaction read write isolation level read commited;
    ```
    1.2.3. ExtendReservation
    ```sql
    -- аномалии косой и фантомной записи не страшны, тк работаем с единственной уже
    -- существующей записью.
    -- read commited недостаточен, нужна гарантия неизменяемости значения при повторном
    -- чтении, тк при попытке одновременной покупки и продления бронирования можно
    -- стереть информацию о покупке
    start transaction read write isolation level repeatable read;
    ```
    1.2.4. BuyFree
    ```sql
    -- аномалия косой записи не страшна, тк работаем с единственной записью.
    -- после проверок выполняется insert, целостность обеспечивает ключ (FlightId,
    -- SeatNo); при гонке один insert победит, второй корректно получит конфликт =>
    -- двойной продажи не будет
    start transaction read write isolation level read commited;
    ```
    1.2.5. BuyReserved
    ```sql
    -- аномалии косой и фантомной записи не страшны, тк работаем с единственной уже
    -- существующей записью.
    -- read commited недостаточен, нужна гарантия неизменяемости значения при повторном 
    -- чтении, тк при попытке одновременной покупки и продления бронирования можно
    -- стереть информацию о покупке
    start transaction read write isolation level repeatable read;
    ```
    1.3.1. FlightsStatistics
    ```sql
    -- результат должен отражать согласованное состояние на момент запроса; одного
    -- снимка без грязных чтений достаточно.
    -- read uncommited недостаточен, тк в результат не должны попадать бронирования/
    -- продажи из незавершенных транзакций
    start transaction read only isolation level read commited;
    ```
    1.3.2. FlightStat
    ```sql
    -- аналогично FlightsStatistics, частный случай статистики по одному рейсу
    start transaction read only isolation level read commited;
    ```
    1.4. CompressSeats
    ```sql
    -- аномалия косой записи не страшна, тк нет глобального инварианта, который
    -- процедура может нарушить, процедура выполняется над одним множеством сущностей -
    -- все брони рейса, и любая конкурентная операция приведет к конфликту по
    -- вставляемой/удаляемой строке, либо по ключу (FlightId, SeatNo)
    -- repeatable read недостаточен, тк возможна аномалия фантомного чтения: например
    -- после копирования всех записей в TempReservations в другой транзакции добавилась
    -- запись, то она удалится в процессе CompressSeats (возможны потерянные
    -- бронирование/покупка)
    start transaction read write isolation level snapshot;
    ```
2. Сценарий

    2.0. Общий план
    - сервис выполняет запрос к базе данных показать информацию о свободных местах
    - пользователь выбирает место из свободных мест, выбирает из опций бронирование/покупка
    - в случае бронирования сервис требует аутентификации
    - сервис выполняет бронирование/покупку выбранного места
    2.1. Запрос списка свободных мест
    ```sql
    start transaction read only isolation level read commited; 
    select SeatNo from FreeSeats(:fid);
    commit;
    ```
    2.2. Взаимодействие с пользователем
    - пользователь выбирает место среди отображенных
    - пользователь выбирает опцию бронирование/покупка
    - если выбрано бронирование требуется аутентификация, если пользователь не выполнил вход в систему заранее, то ему предлагается войти / создать аккаунт
    - в случае создания нового аккаунта:
        ```sql
        start transaction read write isolation level read commited;
        select RegisterUser(:uid, :pass);
        commit;
        ```
        пока создать аккаунт не удалось, пользователь должен повторить попытку

    2.3. Действия с местом
    ```sql
    start transaction read write isolation level read commited;
    select Reserve(:uid, :pass, :fid, :sn);
    commit;
    -- или
    start transaction read write isolation level read commited;
    select BuyFree(:fid, :sn);
    commit;
    ```
    Reserve и BuyFree возвращают true, если операция завершилась успешно. в случае ошибки сервис сообщает об ошибке пользователю
